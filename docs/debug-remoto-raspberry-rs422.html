Reflow Oven · Backend · .NET 10

Debug remoto na Raspberry Pi via VS Code Remote-SSH

Editar e depurar do notebook, mas executar o backend na Raspberry — onde está a comunicação serial RS422 com a placa STM32.

Resposta curta

Sim, é possível e é exatamente o caso de uso do Remote-SSH. O VS Code instala um server na Pi; o build, o processo dotnet, o debugger (vsdbg) e o acesso à porta serial rodam na própria Raspberry. Você só vê a interface no notebook. Assim o driver Rs422PowerBoard abre o /dev/tty* real e fala com a placa.

1 · Como funciona

No Remote-SSH o VS Code se divide em duas metades:

┌──────────────── NOTEBOOK ────────────────┐ ┌──────────── RASPBERRY PI (ssh reflow-oven) ────────────┐ │ VS Code (UI / janela / extensões de tema)│ SSH │ VS Code Server (~/.vscode-server) │ │ │ ◀────▶ │ • build dotnet • debugger vsdbg │ │ Painéis: editor, PORTS, RUN AND DEBUG │ │ • processo ReflowOven.Api ──▶ /dev/ttyS0 (RS422) │ │ │ │ • Postgres em Docker (localhost:5432 = a própria Pi) │ └───────────────────────────────────────────┘ └─────────────────────────────────────────────────────────┘

Consequências práticas:

  • Os breakpoints, variáveis e o passo a passo são do processo que roda na Pi.
  • O System.IO.Ports.SerialPort abre a UART real da Raspberry — é por isso que precisa ser ali.
  • localhost dentro do código passa a ser a Pi (ex.: a connection string Host=localhost;Port=5432 aponta para o Postgres que sobe na própria Pi).
  • Os arquivos .vscode/launch.json e .vscode/tasks.json já existem no repo e usam ${env:HOME}/.dotnet — então funcionam igual na Pi, sem edição.

2 · Pré-requisitos

No notebook

  • VS Code + extensão Remote - SSH (ms-vscode-remote.remote-ssh).
  • SSH configurado para a Pi. No notebook, crie/edite o ~/.ssh/config e ajuste as permissões:
mkdir -p ~/.ssh

cat > ~/.ssh/config <<'EOF'
Host reflow-oven
    HostName raspberrypi.local
    User reflow-oven
    IdentityFile ~/.ssh/MASTER_id_ed25519
    IdentitiesOnly yes
EOF

chmod 700 ~/.ssh
chmod 600 ~/.ssh/config
chmod 600 ~/.ssh/MASTER_id_ed25519        # chave privada
chmod 644 ~/.ssh/MASTER_id_ed25519.pub    # chave pública

ssh reflow-oven        # testa a conexão (na 1ª vez, confirme o fingerprint com "yes")
Os campos / as permissões

HostName raspberrypi.local resolve por mDNS (mesma rede LAN; se não resolver, troque pelo IP da Pi). User reflow-oven é o usuário na Raspberry; IdentityFile aponta a sua chave privada e IdentitiesOnly yes força o SSH a usar só ela (evita "Too many authentication failures"). Os chmod são obrigatórios: o SSH ignora a chave/config se a permissão estiver frouxa demais. Ajuste o nome da chave se a sua for diferente.

Na Raspberry

  • Raspberry Pi OS 64-bit (arm64) — o C# Dev Kit e o debugger vsdbg exigem 64 bits (veja a nota em Observações se a sua for 32-bit).
  • .NET 10 SDK em ~/.dotnet (mesmo layout do note; o global.json fixa a versão 10.0.108).
  • Docker + Docker Compose (você já instalou).
  • git e o repositório clonado na Pi (o código precisa estar lá, não montado do note).
# na Pi
git clone https://github.com/LegiusAndrade/reflow-oven-backend.git
cd reflow-oven-backend

1 Conectar via Remote-SSH

No notebook, abra a paleta de comandos (Ctrl+Shift+P) e rode:

Remote-SSH: Connect to Host…   →   reflow-oven

Uma nova janela abre já dentro da Pi. Na primeira conexão o VS Code baixa e instala o server na Raspberry (demora um pouco). O canto inferior esquerdo passa a mostrar “SSH: reflow-oven” — confirme que está verde antes de seguir.

2 Abrir o projeto (clonado na Pi)

File → Open Folder… e escolha o caminho do clone na Pi (ex.: /home/lsilva/reflow-oven-backend). O seletor de arquivos já lista o disco da Raspberry, não o do note.

3 Instalar as extensões C# no remoto

Extensões de linguagem precisam estar instaladas no contexto SSH (não basta tê-las no note). O repo já recomenda as certas em .vscode/extensions.json, então o VS Code oferece um botão “Install in SSH: reflow-oven”:

  • ms-dotnettools.csdevkit — C# Dev Kit
  • ms-dotnettools.csharp — C# (traz o debugger vsdbg, baixado automaticamente no server)
Dica

Na aba de extensões, a seção “SSH: reflow-oven — Installed” mostra o que está instalado no remoto. As duas acima precisam aparecer ali.

4 Conferir o SDK .NET 10 na Pi

O terminal integrado (Ctrl+`) já é um shell da Pi. Como o SDK fica em ~/.dotnet (fora do PATH global):

export DOTNET_ROOT="$HOME/.dotnet"
export PATH="$HOME/.dotnet:$HOME/.dotnet/tools:$PATH"
dotnet --info          # deve listar o SDK 10.0.108 (arm64)

Se o SDK ainda não estiver lá, instale com o script oficial (sem precisar de root):

curl -sSL https://dot.net/v1/dotnet-install.sh | bash -s -- --version 10.0.108 --install-dir "$HOME/.dotnet"
Nota

A tarefa de build do projeto (.vscode/tasks.json) já chama o dotnet pelo caminho absoluto ${env:HOME}/.dotnet/dotnet e exporta DOTNET_ROOT, então o F5 compila mesmo sem o PATH ajustado. O export acima é só para usar dotnet à mão no terminal.

5 Subir o PostgreSQL (Docker)

O backend migra e faz seed no startup, então o banco precisa estar no ar na Pi:

docker compose up -d
docker compose ps        # postgres deve estar "healthy"

Como tudo roda na Pi, o Host=localhost;Port=5432 do appsettings.json já bate com esse container — nada a mudar.

6 Liberar a serial RS422

a) Descobrir o dispositivo

ls -l /dev/ttyAMA0 /dev/ttyS0 /dev/ttyUSB* 2>/dev/null
dmesg | grep -i tty            # ajuda a identificar a UART/conversor usado

Tipicamente: /dev/ttyAMA0 ou /dev/ttyS0 (UART do header GPIO) ou /dev/ttyUSB0 (conversor USB↔RS422).

b) Dar permissão de acesso à porta

Adicione seu usuário ao grupo dialout e reabra a sessão SSH (reconectar a janela Remote-SSH) para o grupo valer:

sudo usermod -aG dialout "$USER"

c) (Raspberry Pi) habilitar a UART do header

Se usar a UART do GPIO (não um conversor USB), libere o hardware e desligue o console serial de login para não brigar pela porta — via sudo raspi-config → Interface Options → Serial Port:

  • “login shell over serial?” → No
  • “serial port hardware enabled?” → Yes

d) Apontar o backend para a placa real

A seleção da placa é por configuração. Por padrão o appsettings.json usa Hardware:Mode=Simulated (o SimulatedPowerBoard). Para usar a placa de verdade, mude para Rs422 — o jeito mais limpo no debug é via variável de ambiente na própria config de launch (próximo passo):

ChaveValorEfeito
Hardware__ModeRs422usa Rs422PowerBoard (a placa real) em vez do simulador
System__ModeLinux(opcional) usa o LinuxSystemController real — nmcli/timedatectl/systemctl, métricas de /proc·/sys
Atenção — o driver RS422 é um stub

Hoje Rs422PowerBoard é um esqueleto: todos os métodos lançam NotSupportedException (“RS422 power-board protocol não implementado”). Ou seja, depurar na Pi é justamente o que destrava implementá-lo — embrulhar o System.IO.Ports.SerialPort e falar o framing/CRC/protocolo do STM32 em src/ReflowOven.Infrastructure/Hardware/Rs422PowerBoard.cs.

Enquanto o protocolo não estiver pronto, a API sobe com Rs422, mas qualquer chamada à placa (ler sensores, iniciar run) vai estourar a exceção. Para ter a API inteira de pé enquanto desenvolve, deixe Simulated e coloque breakpoints só no caminho da serial, implementando incrementalmente.

7 Depurar (F5) com a placa real

O repo já traz a configuração “Debug API (.NET 10)” em .vscode/launch.json — ela compila (preLaunchTask build), sobe a API com o debugger anexado e já exporta DOTNET_ROOT/PATH e ASPNETCORE_ENVIRONMENT=Development.

Para depurar contra a RS422, acrescente as variáveis ao bloco env dessa config (ou duplique-a como “Debug API (RS422 na Pi)”):

{
  "name": "Debug API (RS422 na Pi)",
  "type": "coreclr",
  "request": "launch",
  "preLaunchTask": "build",
  "program": "${workspaceFolder}/src/ReflowOven.Api/bin/Debug/net10.0/ReflowOven.Api.dll",
  "cwd": "${workspaceFolder}/src/ReflowOven.Api",
  "env": {
    "ASPNETCORE_ENVIRONMENT": "Development",
    "DOTNET_ROOT": "${env:HOME}/.dotnet",
    "PATH": "${env:HOME}/.dotnet:${env:HOME}/.dotnet/tools:${env:PATH}",
    "Hardware__Mode": "Rs422",
    "System__Mode": "Linux"
  },
  "console": "internalConsole"
}

Pressione F5. Coloque breakpoints clicando na margem esquerda de qualquer .cs — eles param no processo que roda na Pi.

Esperado e benigno

O debugger parando em ValidationAppException / NotFoundException / ConflictException é fluxo normal de validação (o ExceptionMiddleware converte em 400/404/409 — nunca crasha). Para não ser interrompido nelas: painel RUN AND DEBUG → BREAKPOINTS e desmarque “User-Unhandled Exceptions”. Você continua vendo os erros de verdade (que viram 500).

8 Acessar a API a partir do notebook

A API escuta em http://localhost:5248 na Pi. O VS Code faz port forwarding automático: o painel PORTS mostra a 5248 encaminhada e você abre http://localhost:5248 direto no navegador do note.

  • Referência da API (Scalar): http://localhost:5248/scalar
  • OpenAPI: http://localhost:5248/openapi/v1.json
  • Login dev: usuário semeado (ex.: lucas.silva) com senha reflow1234.

Se a porta não aparecer sozinha, no painel PORTS clique em Forward a Port e informe 5248. Para apontar o front (reflow-oven-front) a esse backend, use essa mesma URL encaminhada.

Observações importantes

  • Driver RS422 = stub. Reforçando: Rs422PowerBoard ainda não implementa o protocolo (é o trabalho a fazer na Pi). Veja o passo 6d.
  • System:Mode=Linux exige privilégios. As leituras de OS funcionam, mas as mutações (rede via nmcli, relógio via timedatectl, reboot/shutdown via systemctl) precisam das regras de sudoers/polkit correspondentes. Em dev você pode deixar System:Mode=Simulated e só ligar a placa (Hardware:Mode=Rs422).
  • Configs versionadas funcionam na Pi. launch.json/tasks.json usam ${env:HOME}, então não há nada específico do note embutido.
  • Build em ARM é mais lento. O primeiro restore/build na Raspberry demora bem mais que no note — é normal; as compilações seguintes são incrementais.
  • Pi 32-bit (armhf): o C# Dev Kit não traz debugger para 32 bits. Use Raspberry Pi OS 64-bit (recomendado) ou, em último caso, depure com netcoredbg — mas o caminho suportado é arm64.

Solução de problemas

SintomaCausa provável / correção
Breakpoint não para (fica “oco”)As extensões C# não estão instaladas no remoto — confira a seção “SSH: reflow-oven — Installed” (passo 3).
Permission denied ao abrir /dev/tty*Falta o grupo dialout — rode o usermod e reconecte a sessão SSH (o grupo só vale em nova sessão).
UnauthorizedAccessException / porta ocupada na UARTO console serial de login está usando a porta — desligue-o no raspi-config (passo 6c).
dotnet: command not found no terminalExporte DOTNET_ROOT/PATH (passo 4). O F5 não precisa disso — a task usa caminho absoluto.
API não conecta no bancodocker compose ps — suba/aguarde o Postgres ficar healthy (passo 5).
http://localhost:5248 não abre no noteVeja o painel PORTS; encaminhe a 5248 manualmente se preciso (passo 8).
Toda chamada à placa lança NotSupportedExceptionEsperado: Rs422PowerBoard é stub. Implemente o protocolo ou volte para Hardware:Mode=Simulated.
